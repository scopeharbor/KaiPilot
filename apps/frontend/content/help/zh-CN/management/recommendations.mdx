# 智能推荐：建议的产生、评估与采纳

「智能推荐」是 AI 基于项目事实给出的建议收件箱。每条推荐都带着**证据（evidence）**、**置信度（confidence）**与**新鲜度（freshness）**，供你判断"为什么现在需要处理、依据是什么"。推荐本身不产生任何数据变更——**只有你显式确认后，才进入对应的落地流程**。

## 核心概念

| 概念                 | 含义                                             | 你该看什么                               |
| -------------------- | ------------------------------------------------ | ---------------------------------------- |
| 证据（evidence）     | 推荐所依据的项目事实（任务、依赖、风险、进度等） | 证据是否真实、是否过时                   |
| 置信度（confidence） | 模型/规则对建议成立的把握程度                    | 低置信度建议谨慎采纳，不确定项会明确标注 |
| 新鲜度（freshness）  | 推荐所依赖数据的时效                             | 数据变化或过期时，卡片会提示重新评估     |
| 影响（impact）       | 采纳该建议可能带来的改动范围                     | 影响大（如批量改任务）时先预览再确认     |
| why-now              | 为什么是"现在"需要处理                           | 结合当前项目执行状态判断时机             |

## 适用范围

- 需要 `recommendation:view` 权限的用户（项目经理、组织管理员等）。
- 建议按组织隔离内的项目数据生成，跨组织数据不参与计算。

## 建议如何产生

1. 系统收集当前项目的可分析执行数据（任务、依赖、风险、进度等）。
2. AI 与规则通道基于事实生成建议，并附带证据引用、置信度与新鲜度标注。
3. 建议进入「智能推荐」收件箱等待处理；数据更新后，建议会按需重新生成。

建议的产出受**反幻觉检查（HL-001~HL-010）**约束：日期逻辑、依赖环路、规则校验与置信度评分都会挡住"凭空结论"，低置信度或证据不足的建议会明确标注，而不是伪装成确定事实。

## 如何处置一条推荐

| 次序 | 动作           | 要点                                                                                            |
| ---- | -------------- | ----------------------------------------------------------------------------------------------- |
| 1    | 看证据         | 确认推荐依据的事实存在且最新                                                                    |
| 2    | 看置信度与影响 | 低置信度、大影响的推荐优先走预览确认流程                                                        |
| 3    | 接受           | 进入 preview/confirm 预览确认流程——按类型进入对应处置（转为任务、风险等），创建动作仍需人工确认 |
| 4    | 拒绝           | 可选记录原因，帮助后续建议收敛误报                                                              |
| 5    | 定期复查       | 已接受但数据变化的推荐，若新鲜度下降，卡片会提示重新评估                                        |

## 推荐的类型与处置路径

推荐最终会落到不同的处置通道，但**前置动作完全一致：先预览、后确认**：

- 转为**任务**：确认后进入任务创建流程，日期/依赖等仍按项目规范人工核对。
- 转为**风险**：确认后进入风险登记册，概率/影响等字段按采纳内容落库并标注来源。
- 转为**变更/报表素材**：作为影响分析或报表的输入建议，写入与否由对应流程的人工确认决定。

无论在哪个通道，**AI 都不自动执行**：在完成 preview/confirm 之前，不创建任务、不创建风险、不修改任何项目事实。

## 减少噪音的最佳实践

1. **补齐项目数据**：任务依赖、风险登记、里程碑完整时，建议的依据更扎实，误报明显减少。
2. **拒绝时留原因**：帮助模型收敛同类误报，而不是同一噪音反复出现。
3. **按状态分批处理**：先处理新鲜度高、影响大的推荐，再回头看低置信度项。
4. **定期核对已采纳项**：采纳后若基础数据变化，重新评估而不是默认继续执行。

## 验证结果

- 每条推荐都标注了依据与置信度，不会出现"凭空结论"。
- 在你完成 preview/confirm 确认之前，系统不会创建任何任务/风险/变更——可在审计日志中核对"只读、未写"。
- 拒绝并记录原因后，同类建议会减少误报。

## 常见问题

**症状：建议看起来过时。**
可能原因：依赖数据新鲜度不足。
检查：卡片上的 freshness 与生成时间；数据更新后建议会重新生成。

**症状：接受建议后没看到新任务。**
可能原因：preview/confirm 尚未完成。
处理：回到建议卡片完成确认；AI 建议不自动落库是产品红线。

**症状：看不到智能推荐入口。**
可能原因：缺少 `recommendation:view` 权限。
处理：联系组织管理员调整角色；权限判定以服务端为准。

**症状：建议与实际情况不符。**
可能原因：基础数据（任务依赖、风险登记）不完整。
处理：先补齐项目数据，再重新生成推荐。

## 安全与限制

- **建议不自动落库**：确认动作受权限与审计约束，任何写操作都以你的显式确认为前提。
- **组织隔离**：推荐只基于当前组织内的项目数据生成，跨组织数据不参与计算。
- **反幻觉边界**：HL-001~HL-010 检查约束生成内容；低置信度建议明确标注，不充当确定结论。
- 建议仅作决策参考，不替代人工的专业判断。
